LINQA PRODUCT READINESS REVIEW
Date: October 15, 2026
Scope: Targeted local source review and selected tests. This is not a full security audit, penetration test, or production certification.

1. SECURITY LEVEL AND EXPOSURE IF COMPROMISED

Security protections exist, but the system cannot yet be certified as secure from this review.

Online API/database breach:
- Potential exposure includes account/profile data, conversation membership, device identifiers, activity metadata, and stored ciphertext.
- Properly encrypted message content should remain protected if client keys remain safe. That guarantee still needs end-to-end verification across the deployed system.

Hacked phone, online or offline:
- Displayed/decrypted messages, accessible files, sessions, and potentially encryption keys may be exposed.
- End-to-end encryption cannot protect content inside a fully compromised client.

Offline extraction of app storage:
- The mobile outbox stores encrypted message envelopes.
- Account, conversation, and device identifiers, timestamps, and delivery state are readable database fields.
- The inspected outbox implementation does not configure whole-database encryption.
- Source: clients/mobile/src/messaging/sqlite-outbox.ts

Compromised development computer:
- Debug builds and ADB connections create additional access to application data and runtime behavior.
- The current Galaxy/LG configuration is a development environment.

Concrete concerns requiring follow-up:
- SECURITY-REVIEW.md records historical release-signing password exposure. Credential/key rotation was not verified in this review. Secret values are not reproduced here.
- clients/mobile/services/conversation-gate.ts calls protectionLevel() but does not enforce an acceptable returned protection level. This check alone does not establish hardware-backed or OS-wrapped key protection.

Limits:
- Production configuration, live authorization, provider configuration, credential rotation, and all application routes were not comprehensively verified.
- Security-model documentation describes intended guarantees; it does not independently prove that every deployed flow meets them.

2. CHAT ROUTE SECURITY VALIDATION SUITE

Recommendation: Maintain and extend a dedicated route-security suite using the existing Vitest runner. Jest is optional and is not required to improve security coverage.

Existing coverage includes:
- Missing authentication.
- Insufficient scope.
- Conversation membership filtering.
- Rejection of cleartext attachment metadata.

Validation performed:
Command, run from server/:
node node_modules/vitest/vitest.mjs run src/tests/chats-inbox.route.test.ts src/tests/chat/shared-attachment.routes.test.ts src/tests/production-auth-policy.test.ts src/tests/auth-security.test.ts

Result: 4 test files passed; 32 tests passed.
This was a targeted run, not a full database integration run or penetration test.

Recommended dedicated security command and coverage:
- Expired and forged tokens, incorrect issuer/audience.
- Revoked devices and sessions.
- Cross-account access and object ownership.
- Removed conversation members.
- Attachment ownership and access.
- WebSocket authentication and authorization.
- Logout and account-switch isolation.

Adding Jest would introduce another runner without improving security by itself. No new runner or suite was introduced during this review.

3. GITHUB ACTIONS CI/CD AND IMAGE BUILDING

GitHub Actions workflows exist, but automatic image build/test on every main push is incomplete.

.github/workflows/ci.yml:
- Runs on pushes to main/develop, pull requests, and manual requests.
- Tests/builds the server, web client, and Rust core.

.github/workflows/api-image.yml:
- Runs on v* release tags and manual requests.
- Builds, publishes, and signs the API Docker image.
- Records the immutable deployable image digest.
- Does not trigger on every main push.
- Does not have a test dependency in that workflow.

.github/workflows/mobile-release.yml:
- Manually starts Android/iOS EAS builds.
- It is separate from the API Docker image workflow.

Recommended changes for the API image pipeline:
- Add a main-push trigger.
- Require passing tests before publishing the image.
- Add image smoke tests and image security checks.

Verification limits:
- Workflow files alone do not confirm successful GitHub runs, configured secrets, enforced branch protection, or production deployment.
- This review inspected local workflow definitions; it did not verify live GitHub execution.

READINESS CONCLUSION

Do not treat this targeted review as production security clearance. Resolve or verify the historical signing-credential exposure, validate client key-protection enforcement, broaden security-boundary tests, and connect image publishing to required passing checks.

No application source or workflow files were changed during the review. This report records findings and recommendations only.
