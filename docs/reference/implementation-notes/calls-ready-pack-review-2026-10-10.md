# Review of linqa-calls-Ready ? 2026-10-10

Verdict: useful implementation source, not safe to integrate unchanged. The listed adapter/configuration connections are necessary but insufficient. This was a code review with targeted reproductions, not a complete native build, cryptographic audit, or production approval. No migration, TURN secret change, phone installation, or replacement of the running call system was performed.

## What fits

The pack explicitly says it is not MLS. It proposes a per-call random key hybrid-sealed to recipient devices, identity signatures on key delivery and signaling, XChaCha20-Poly1305 signaling, and WebRTC DTLS-SRTP media. That approach can be adapted to Linqa's existing hybrid Rust chat primitives. Server relay checks sender and recipient call participation. The root accepts an injected native binding and the public entry point does not export jsCoreBinding.ts; tests intentionally use the JavaScript binding. Keep that binding test-only, with a release dependency/import check.

## Required corrections and connections

1. **Native cryptographic API is missing, not merely misnamed.** The requested `sealToDevice`, `openSealed`, and `signWithIdentity` are declarations in the pack adapter. Linqa's existing Expo module exposes message encryption/decryption and key package operations, not these operations. Rust `crypto/sealed_sender.rs::seal/open` have a different format, credential requirement, and no arbitrary caller AAD input; directly renaming those is incorrect. Add domain-separated call-envelope/signing operations in Rust and expose them through both native bridges. Verify native round-trip, modified AAD, wrong device, signature failure, and Rust/JS wire compatibility. Linqa's current key setup also uses exportKeyMaterial, so the claim that identity private keys never enter JS requires a separate key-lifecycle review.

2. **Key-directory contract does not match.** The pack expects `/keys/users/:userId/devices` with base64 x25519/mlkem768/ed25519 fields. Linqa currently retrieves signed `packageBase64` records from `/v1/users/:userId/key-packages`. Adapt using existing verification, identity/device checks, expiration and revoked-device filtering. Do not simply decode and trust raw keys. The pack's `HttpKeyDirectory.device()` returns cached keys without applying its TTL; `LinqaCallCrypto.signingKey()` caches forever for that instance. Define revocation/pinning semantics.

3. **Authentication must use the existing principal.** `jwt-calls-auth.ts` reads sub/userId and uses the separately supplied device claim, checking only ownership/revocation. Linqa uses user_id, signed device_id and scopes, plus configured issuer/audience and allowed JWT algorithms. Enforce the signed device claim and relevant scopes using existing authentication; do not accept another owned device just because its ID was supplied in a header or socket auth.

4. **Backend and database mismatch.** Linqa is Fastify/ws with SQL migrations, not NestJS/socket.io/Prisma. The supplied Prisma models persist reports and push tokens, not live call state. Adapt into current PostgreSQL services, existing safety reporting and realtime transport, or explicitly design a separate interoperable service. Do not run prisma migrate dev against the existing database as a shortcut. Keep current call history/status and scheduled-call integration.

5. **Redis store cannot be swapped in as advertised.** `CallsService` makes synchronous store reads and mutates shared CallRecord objects in place; RedisCallsStore is asynchronous, lacks all/activeCallsForDevice/ringingFor/handoffsForCall, and does not persist subsequent in-place changes automatically. CallsModule still registers the in-memory store. Redesign a common asynchronous repository with persisted updates, atomic participant/handoff changes, distributed deadlines and device presence. A socket.io Redis adapter alone will not fix this.

6. **Lifecycle defects must be repaired before replacing the hardened controller.** Pack CallEngine waits up to four seconds for leave acknowledgment before stopping media. getUserMedia/getDisplayMedia/openCamera lack post-await ended/generation checks; ending while a prompt is pending can attach tracks after teardown. Its call listeners are installed only after initial media acquisition, creating a window for lost ended/joined events. Root cleanup closes signaling but does not explicitly end the active engine. Add immediate cleanup, operation guards, early subscriptions, failed-start cleanup and bounded queues.

7. **Three manager defects were reproduced against transpiled supplied source:** concurrent startCall calls both reach launch; call:ring-cancelled during delayed acceptEnvelope is lost and the ring subsequently reappears; engine startup ending before subscribe triggers `Cannot access off before initialization` because subscribe invokes its callback immediately. Reproduction: `node tmp/call-ready-review.cjs` (external/native operations mocked). The manager's busy flag is not a lock, and async ring handlers need cancellation/account-generation checks.

8. **Native integration still requires builds and device tests.** The pack supplies Android/iOS blur, push helpers and an iOS Broadcast Upload Extension; their presence is not build or behavior validation. iOS capabilities are reported true without verifying the configured extension. Preserve existing recorder integration and Android MediaProjection configuration. Verify current Expo/RN/WebRTC versions rather than importing the pack's older development versions. Test LG/Galaxy and iOS cold-start ringing, capture, decline/end, reconnect, cancellation, handoff and logout.

9. **TURN needs compatible configuration and reachability.** Linqa uses TURN_SHARED_SECRET; the pack reads TURN_SECRET. Use one secret consistently on API and coturn without exposing it. Validate URLs, expiry, public reachability, credentials and relay-only behavior. Pack TURN returns STUN-only when credentials are absent; verify privacy policy is preserved. No secret was read or modified during review.

## Security scope

This is a custom shared-key call protocol, not MLS. A call key remains in JS even with native identity-key sealing/signing; excluding jsCoreBinding prevents the proposed JS identity private-key implementation from shipping but does not move all call cryptography into Rust. The pack retains one key through participant additions/departures: no MLS-style epoch rekeying, forward-secrecy or post-compromise-security guarantee should be claimed. Replay memory is limited to the most recent 4096 nonces, so older replays become acceptable after eviction; envelope timestamps also need strict finite-number/schema validation. Establish explicit call-context binding and participant/key-change verification policy before production use.

Recommended order: define the Rust/native call API and authenticated key-directory adapter; repair authentication and call lifecycle; adapt persistence/signaling to Fastify/PostgreSQL; connect native actions and TURN; run native cryptographic interoperability tests and real-device acceptance tests; only then consider enabling all pack actions. Use jsCoreBinding exclusively in isolated tests.
