DETAILED FINDINGS
-----------------

C-01 CRITICAL - Multi-account flow can mint a session for another user

Evidence:

  * server/src/routes/multi-account.routes.ts:89-110 accepts targetUserId directly
    from any bearer with account:write. The source comment at lines 102-103 itself
    states that production requires a freshly authenticated add-account ceremony,
    but no such proof is enforced.
  * The route does not first prove that the caller owns or is a member of the
    supplied installationId.
  * server/src/services/multi-account.service.ts:60-117 adds the arbitrary user if
    that user merely has a verified mobile number.
  * server/src/services/account-switch.service.ts:18-36 checks only that the target
    account is present on the installation; it does not prove the caller controls
    the target identity or that the current device is trusted for it.
  * server/src/services/account-session-issuer.ts:12-18 then creates a real session
    and access/refresh tokens for the target user.

Impact: With guessed, discovered, or leaked UUIDs, an authenticated attacker may be
able to bind a victim account to an installation and mint a victim session. This is
an account-takeover design flaw.

Recommendation:

  1. Disable the v5 add/switch endpoints immediately or feature-gate them off.
  2. Require a short-lived, single-use, audience-bound proof created by fresh
     authentication of targetUserId (OTP/passkey plus device possession).
  3. Bind the proof to target user, installation, device, action, nonce, and expiry.
  4. Verify caller membership and trusted-device membership on every installation
     operation. Do all proof consumption, binding, and session issuance in one
     serializable transaction.
  5. Add negative integration tests for arbitrary targetUserId, foreign
     installationId, foreign deviceId, replay, race, and removed membership.

H-01 HIGH - Production token issuer and verifier are incompatible

Evidence:

  * server/src/auth/tokens.ts:23-39 always signs access tokens with the local HS256
    secret.
  * server/src/auth/jwt.ts:22-30 requires remote JWKS in production and permits only
    RS256, ES256, or EdDSA when JWKS is configured.
  * server/src/services/session.service.ts:49-55 and 118-124 use the HS256 issuer for
    normal and refreshed sessions.

Impact: Tokens issued by Linqa in production cannot pass Linqa's production
authenticator. Authentication will fail closed, causing a production outage. Teams
may be tempted to weaken NODE_ENV or verifier settings to restore service, creating
a security regression.

Recommendation: Select one explicit trust architecture. Prefer asymmetric signing
with a KMS/HSM-backed private key, publish/consume a pinned JWKS, set kid, and rotate
keys. If an external identity provider is authoritative, stop locally issuing access
tokens and exchange sessions through that provider. Add a production-mode end-to-end
test that issues, verifies, refreshes, and revokes a token.

H-02 HIGH - Android release is signed with the bundled debug key

Evidence: clients/mobile/android/app/build.gradle:100-116 defines the standard debug
credentials and applies signingConfigs.debug to the release build.

Impact: Release authenticity and update trust are not production grade. Anyone with
the well-known debug key can produce an identically signed package in channels that
do not add a separate trusted signature layer. Store deployment may also be rejected
or create an irreversible signing lineage problem.

Recommendation: Remove release fallback to debug signing. Load a production upload
key from a protected CI secret or use Play App Signing, fail the release build if it
is absent, enable R8/resource shrinking after compatibility testing, and verify the
final AAB certificate fingerprint in CI.

H-03 HIGH - The shipped web UI is still driven by mock/plaintext workflows

Evidence:

  * clients/web/src/services/CoreBridge.ts:1-17 states that the main bridge uses
    in-memory mock data; isNativeLoaded() returns false at lines 27-33.
  * clients/web/src/App.tsx:28, components/ChatView.tsx:85 and 166, and
    components/SettingsPanel.tsx:58-59 and 119 call this mock bridge directly.
  * CoreBridge.ts:47-61 marks messages "sent" without secure transport.
  * CoreBridge.ts:68-72 generates a device-link display code with Math.random().
  * DemoCoreAdapter stores plaintext messages in localStorage at lines 113-151.

Impact: The visible web product can simulate sends, devices, and device linking while
not performing those secure operations. This is a severe product-integrity and user
safety problem for an application represented as private/E2EE. It also risks
plaintext persistence in the browser when demo mode is active.

Recommendation: Remove mock operations from production bundles, make the production
UI depend only on a successfully initialized secure adapter, block all send/link
actions when it is unavailable, use CSPRNG/server challenges for real linking, and
add an end-to-end assertion that production cannot render a successful send from a
mock adapter.

H-04 HIGH - Production capabilities are intentionally incomplete

Evidence:

  * server/src/bootstrap/service-container.ts:322-323 always installs fail-closed
    MLS and MLS-group providers.
  * server/src/runtime/registry-factory.ts:24 makes secure-core readiness depend on
    an external artifact path/hash; secure-messaging is derived from that and other
    services at line 56.
  * server/src/tests/final-runtime.test.ts explicitly verifies that final readiness
    remains closed until the secure core is integrated.
  * The LinqaSend mobile client documents that no licensed money movement provider
    is configured (clients/mobile/services/linqasend.service.ts:52-58).

Impact: Core product claims and several workflows are not deployable as complete
production capabilities. Fail-closed behavior is good, but it means the application
is not release-ready.

Recommendation: Define a minimum releasable feature set. Either integrate and
certify each required provider or remove/disable its UI and claims. Treat readiness
as an admission gate and retain the fail-closed behavior.

H-05 HIGH - Secrets are present in a synced workspace as a real .env file

Evidence: server/.env contains populated JWT, contact-discovery, token-vault, TURN,
and CountryLinqa key material. Values were not copied into this report. .gitignore
correctly excludes .env, but the workspace is in OneDrive and no Git repository was
available to prove the file was never committed or shared.

Impact: A copied archive, cloud sync exposure, support upload, or earlier commit can
compromise token signing, encrypted token storage, discovery privacy, TURN access,
and protected CountryLinqa data.

Recommendation: Move secrets to a secrets manager; keep only .env.example locally.
Rotate all populated secrets if sharing cannot be disproved. Add secret scanning to
CI and pre-commit, and use separate purpose-specific keys with identifiers/versions.

M-01 MEDIUM - Release verification is red

Observed results on 2026-08-13:

  * Server build: PASS.
  * Server tests: FAIL, 142 passed / 3 timed out. Failures were route boot tests for
    passkeys, organization authorization, and collaboration.
  * Web production build: FAIL. TypeScript union-narrowing errors in
    clients/web/src/auth/validation.test.ts at lines 8, 9, 15, 16, 22, and 33.
  * Mobile typecheck: PASS.
  * Rust core: PASS, 20 tests total across unit/integration suites.

Impact: A clean reproducible release cannot currently be produced. The server test
timeouts may be performance/flakiness rather than security failures, but red CI
cannot serve as a security gate.

Recommendation: Separate test compilation from production compilation where
appropriate, fix the test narrowing, profile slow app bootstrap, eliminate timing
dependence, and require all release checks to pass from a clean checkout.

M-02 MEDIUM - Deployment manifests lack container hardening

Evidence: k8s/api-deployment.yaml defines replicas, probes, and resource limits, but
does not set runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation:false,
capabilities.drop:[ALL], seccompProfile, serviceAccount restrictions, topology
spread/anti-affinity, PodDisruptionBudget, or NetworkPolicy. The image reference at
line 17 is a replacement placeholder rather than an immutable digest.

Recommendation: Add pod/container security contexts, a minimal service account,
default-deny ingress/egress policies, disruption and spread controls, and admission
verification for signed immutable image digests.

M-03 MEDIUM - Development infrastructure exposes weak services on host ports

Evidence: server/docker-compose.yml publishes PostgreSQL, Redis, MinIO, TURN, and the
MinIO console on all host interfaces by default; it uses static development
passwords and unpinned latest images for MinIO/coturn.

Impact: On a shared or externally reachable developer machine, unauthenticated Redis
and weakly credentialed services may be reachable. Floating tags reduce
reproducibility and supply-chain control.

Recommendation: Bind development ports to 127.0.0.1, add Redis authentication/TLS
where applicable, generate per-developer secrets, and pin images by version/digest.

M-04 MEDIUM - Database TLS is not explicitly required

Evidence: server/src/db/pool.ts:6-14 passes DATABASE_URL without an explicit SSL
policy. Security therefore depends entirely on the connection string/environment.

Recommendation: In production, require certificate-validated TLS and fail boot if
the database connection is plaintext or certificate verification is disabled.

M-05 MEDIUM - Rate limiting is not deployment-aware

Evidence: server/src/app.ts:31 sets trustProxy:false and lines 58-61 apply one global
120/minute limiter. In a Kubernetes ingress deployment, all clients may appear as
the proxy unless topology is configured accordingly.

Impact: Legitimate users can share one quota (easy availability failure), or teams
may broadly enable proxy trust later and permit spoofed forwarding headers.

Recommendation: Configure an explicit trusted proxy/CIDR policy, use a distributed
Redis-backed limiter, and apply tighter route-specific limits to OTP, authentication,
passkey, discovery, upload, and money-related endpoints using account/device/IP
dimensions.

M-06 MEDIUM - Web bearer tokens are readable by JavaScript

Evidence: clients/web/src/app/apiSession.ts stores/reads access tokens from
sessionStorage; SecureDeviceEnrollment.ts:80 writes the enrolled token there.

Impact: Any XSS or compromised same-origin script can steal the bearer token.

Recommendation: Minimize token lifetime and scopes, deploy a strict CSP on the web
origin, avoid third-party scripts, consider a backend-for-frontend with HttpOnly,
Secure, SameSite cookies, and never place refresh tokens in browser storage.

L-01 LOW - Server Helmet disables Content-Security-Policy

Evidence: server/src/app.ts:48-51 registers Helmet with contentSecurityPolicy:false.
For a JSON API this is less important than on the web frontend, but any HTML/error
surface loses defense in depth. Configure CSP at the actual web origin and document
where it is enforced.

L-02 LOW - Mobile clients have plaintext development API defaults

Evidence: many mobile screens fall back to http://10.0.2.2:8080; web falls back to
http://127.0.0.1:8080. Debug Android explicitly permits cleartext traffic.

Recommendation: Centralize endpoint configuration, require HTTPS/WSS in release
builds, fail release startup on localhost/emulator/plaintext URLs, and keep cleartext
permission debug-only.

L-03 LOW - Android backup posture is ambiguous

Evidence: clients/mobile/android/app/src/main/AndroidManifest.xml:14 sets
allowBackup=true and references secure-store backup/data-extraction rule resources,
but those XML resources were not present in the reviewed source tree.

Recommendation: Verify the final merged release manifest and APK/AAB resources.
Prefer allowBackup=false for this threat model, or explicitly exclude all tokens,
keys, encrypted databases, and SecureStore material from cloud/device transfer.

POSITIVE SECURITY CONTROLS
--------------------------

The following controls are present and should be preserved:

  * Strict Zod environment validation and all-or-none provider configuration.
  * JWT issuer, audience, and algorithm allow-list checks.
  * Production authentication fails closed when JWKS is absent.
  * Short 15-minute access tokens, hashed 48-byte refresh tokens, rotation, and
    refresh-token family revocation on detected reuse.
  * Six-digit OTP generation with crypto.randomInt, salted scrypt storage, constant-
    time verification, challenge expiry/attempt controls in the reviewed service.
  * WebAuthn verifies RP ID, allowed origins, challenges, credential ownership, and
    requires user verification.
  * Authenticated, device-bound realtime sockets and call-participant checks.
  * Parameterized SQL in all sampled runtime paths; no eval/new Function/unsafe DOM
    execution or obvious command injection was found by pattern review.
  * Central error handler avoids returning internal exception detail.
  * Helmet, CORS allow-listing, request body limits, request timeouts, and log
    redaction exist.
  * Object storage, delivery, step-up, MLS, and related providers generally fail
    closed rather than simulate success in production.
  * Rust core uses modern primitives (X25519, ML-KEM, Ed25519, HKDF,
    ChaCha20-Poly1305, Argon2), includes zeroization support, replay protection, and
    passing tamper/wrong-recipient/expiry tests.
  * Production boot has explicit required capability gates.
