Application Security Assessment — Expanded Follow-up
Date: 2026-10-12

Executive summary

The locally available evidence confirms that release-signing credentials were committed to Git history and remain reachable from the current branch and its remote-tracking ref as of the last fetch. Credential rotation and history rewriting are not evidenced in the checkout. This follow-up did not complete a page-by-page review of the full mobile/web route inventory, and it did not access production, provider consoles, live user accounts, or GitHub audit/access records. No new application-code vulnerability was confirmed in this follow-up. This is not a full security clearance.

Historical exposure evidence

- Local Git inspection found the credential file at commit `77fcf52`; its credential-bearing fields occur on lines 3 and 5. The secret values were not copied into this report.
- Commit `d852fcb` deleted/untracked the file; deletion does not purge earlier Git blobs.
- As of the last local fetch, `77fcf52` is reachable from `agent/production-module-hardening` and `remotes/origin/agent/production-module-hardening`, but not from `main` or `origin/main`. The remote tracking ref indicates the commit reached the configured GitHub remote; it does not establish repository visibility or who accessed it.
- No evidence of credential/key rotation or history rewrite was found in the inspected checkout. `thingsdone.txt` contains advice to rotate, not proof that rotation occurred.
- Whether the keystore itself was ever committed was not established; a full-history search for keystore file types was not completed.
- The repository's current visibility, collaborators, forks, clones, and access/audit logs cannot be established from the local checkout.

Deployment, providers, and live verification

Not verified: deployment manifests/configuration, production TLS/WAF/secrets-manager state, CI workflow behavior, or actual deployed build settings. Push, OTP/SMS, TURN, storage, AI, KMS, and other provider behavior were not tested against provider accounts or production. Runtime authorization with live accounts was not tested. The local environment had no authorized production session or account context supplied for these checks; no production probing or credential use was performed.

Credential validity and rotation cannot be confirmed without authorized access to the signing keystore and the relevant Play Console/App Store signing records. Repository access history requires authorized GitHub organization/repository audit logs and visibility/collaborator/fork data; it is not available from the local Git checkout. No passwords, tokens, or signing material were used or reproduced.

Recommendations

1. Treat the historical release credentials as compromised. Rotate the store/key passwords and replace or reset the signing key using the platform's supported process (for example, an upload-key reset where applicable). Confirm and record completion with the release owner; rotation is not evidenced here.
2. Determine whether any corresponding keystore exists in current or historical Git objects and whether the signing credentials remain active. Do this in a controlled environment without printing secret values.
3. Review GitHub repository visibility, collaborators, forks, audit logs, secret-scanning alerts, and push-protection events with an authorized repository administrator. If history cleanup is appropriate, coordinate it with collaborators; a history rewrite does not revoke the credentials.
4. Add ignore rules for `*.jks`, `*.p12`, `*.pfx`, `*.mobileprovision`, `server/.local-vault/`, and `server/key-directory/`, and enable secret scanning/push protection. `.gitignore` already ignores `**/linqa-signing.properties`; the other patterns were identified as a hardening gap.
5. Complete a route-by-route mobile/web inventory and trace each screen's sensitive operations to API authentication, authorization, ownership checks, validation, and rate limits. Start with the pending higher-priority paths above; record routes actually inspected and targeted tests run.
6. Separately review deployment configuration and CI/CD, then validate TLS, secret delivery, and provider settings with authorized production owners.
7. With authorized test accounts, dynamically test direct API requests for cross-account access, IDOR, session/logout/account-switch leakage, upload abuse, and role/ownership boundaries. Do not use real users' accounts or data.

Assessment method and limitations

Static review only; no comprehensive dynamic test or penetration test was performed. The expanded route trace ran out of review capacity before tracing the full mobile/web inventory and all server routes. The approximately 448 server route registrations across 68 files are a count, not a finding-by-finding review. Deployed configuration, provider behavior, credential validity/rotation, repository access history, the existence/accessibility of the keystore, and runtime authorization with live accounts remain unverified. No new code vulnerability was confirmed in this follow-up; absence of findings in unreviewed areas must not be read as evidence those areas are secure.
