HIGHEST-IMPACT IMPLEMENTATION FINDINGS

1. PRODUCTION AUTHENTICATION CONTRACT IS INTERNALLY INCONSISTENT (Critical functionality / High security risk)

`server/src/services/session.service.ts` always issues HS256 access tokens. In production, `server/src/auth/jwt.ts` refuses HS256 and requires a configured remote JWKS with RS256, ES256, or EdDSA. Therefore tokens issued by the application's own OTP/register/session code are not accepted by the production authenticator. This is consistent with the repository's own unchecked requirement: "OIDC/JWKS replaces development HS256 authentication."

Result: phone/email auth may work in development but is not a complete production authentication chain.

2. AUTH CHALLENGE PURPOSE IS NOT ENFORCED DURING LOGIN VERIFICATION (High)

`/v1/auth/challenges/verify` authenticates an existing account after any valid challenge, regardless of whether the challenge purpose was LOGIN, REGISTRATION, ADD_IDENTIFIER, RECOVERY, or HIGH_RISK_ACTION. Purpose is returned by the service but ignored by the route's session-issuance decision. Separate security ceremonies therefore collapse into a general login ceremony.

3. "TEMPORARY" PRE-ENROLLMENT SESSIONS HAVE REAL WRITE SCOPES (High)

OTP verification and registration return a refreshable session before device enrollment/passkey completion, while granting account, CountryLinqa, and LinqaSend read/write scopes. The response says `authenticationRequired: DEVICE_ENROLLMENT_OR_PASSKEY`, but server authorization does not implement a general "temporary session" restriction for those scopes. UI sequencing is not an adequate security boundary.

4. AUTH RATE LIMITING IS INCOMPLETE FOR ABUSE RESISTANCE (Medium/High)

The challenge service limits five challenges per identifier per hour and the app has a general 120 requests/minute limiter, but there is no challenge-specific IP/device risk limiter. An attacker can rotate destination identifiers and generate delivery cost/abuse. Delivery failure also occurs after the challenge transaction commits, leaving a failed challenge that counts toward limits.

5. ANDROID PHONE NORMALIZATION IS US-CENTRIC AND BREAKS INTERNATIONAL NUMBERS (High functionality)

Android `LoginScreen.normalizeIdentifier` strips digits and, for any input with at least ten digits, prefixes `+1` to the last ten digits. A valid non-US E.164 number can be silently transformed into a US number. This contradicts the server and web/Expo E.164-style contract. Android also always requests a REGISTRATION-purpose challenge for the sign-in screen.

6. AUTHENTICATED ANDROID HOME DATA IS STILL A FIXED DEMO PERSONA (Critical integration)

`clients/android/.../crypto/CoreBridge.kt` and `clients/mobile/services/mobile-hub.service.ts` send `x-linqa-demo-user: galaxy`. `server/src/routes/mobile-hub.ts` maps this to fixed demo user/device UUIDs and is disabled in production. Android's MainActivity loads Home data through that bridge even after real auth/enrollment. The authenticated user's account data is therefore not vertically wired to the primary hub.

7. EXPO SESSION LIFECYCLE IS INCOMPLETE (High functionality)

Expo stores per-account access and refresh tokens, but `accessTokenProvider` only returns an unexpired access token. It does not rotate an expired token with the stored refresh token. Normal sessions expire after 15 minutes, after which authenticated screens fail closed until another flow replaces the session.

8. EXPO/MOBILE FEATURE SURFACES ARE PARTLY NON-FUNCTIONAL (High functionality)

- Calls' local QuickCreate handler explicitly closes without performing any action.
- Privacy Center device verification and revocation show "Not available yet" alerts.
- CountryLinqa `full-flow.tsx` uses `renderMockScreen` for its showcase flow.
- Many of the 34 modules are generic action catalogs; an action often routes to another generic module or an unavailable alert rather than an end-to-end workflow.
- Capability gates default many workflows to incomplete unless build-time environment flags are explicitly true.
- There are no Expo/mobile automated tests.

9. WEB IS HONESTLY DEMO-CAPABLE, BUT NOT A FULL LIVE CLIENT (High functionality)

The web client contains DemoMessagingService, DemoCallService, DemoAttachmentService, DemoCoreAdapter, local mock data, and local demo message storage. Runtime banners disclose this, which is good fail-honest behavior, but it means broad "full application" claims are false. The production build also currently fails.

10. MULTI-ACCOUNT IS NOT GENUINELY VERIFIED END TO END (High)

The repository's `FINAL_CHECKLIST.md` leaves every phone, accounts, isolation, switching, and security item unchecked. Server models and route/unit tests exist, and Expo has per-account storage. However:
- no three-physical-device/account release evidence is present;
- notification-to-correct-account activation is not demonstrated;
- the native Android SessionStore holds one current session and relies on server switching rather than retaining complete independent local sessions;
- Android Home remains fixed demo data after switching;
- provider-backed phone intelligence is not proven;
- UI data isolation has no automated client test.

WHAT IS WELL IMPLEMENTED

- Server compiles and its 145 tests currently pass.
- Cryptographic primitives and protocol handling have meaningful Rust tests.
- OTPs use cryptographic randomness, scrypt hashing, attempt counts, expiry, superseding, and database row locking.
- Refresh-token rotation detects previous-token reuse and revokes the token family.
- Device enrollment verifies an Ed25519 proof in tested server code.
- Many sensitive integrations fail closed when unconfigured instead of silently pretending success.
- CountryLinqa and LinqaSend use real migrations and service layers rather than only UI mockups.
- Release governance rejects stale/mismatched/mock/skipped evidence by design.
- Runtime/demo banners are generally honest about insecure mock behavior.

No: these packs are not fully implemented and functional as claimed by their filenames. The strongest portions are the server service/migration breadth, Rust core, and governance/test scaffolding.
